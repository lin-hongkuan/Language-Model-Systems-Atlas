一个 NLP 项目不只是“把模型训练起来”。你需要说明要回答什么问题，哪些证据可以支持结论，以及别人怎样检查结果。CS224N 的 L06 讨论期末项目选项和实践建议；课程每年的具体项目要求可能变化，应以当期项目页面和 handout 为准。

## 1. 把兴趣改写成可检验的问题

“研究检索增强生成”范围太大。把问题缩到可比较的一处，例如：

> 在固定语料、模型和评估集上，增加检索结果数量是否会改善带引用问答的事实正确率？

这句话已经包含了使用场景、要改变的变量和可观测结果。继续问：

- **数据是什么？** 训练集、验证集和测试集怎样划分，是否可能泄漏答案？
- **比较对象是什么？** 先设一个可信基线，再添加你要研究的改动。
- **只改变了什么？** 若检索器、提示词、模型和数据同时改变，就很难解释分数变化。
- **怎样衡量？** 选择与研究问题相关的指标，并抽样检查错误。

## 2. 默认项目与自拟项目

官方课件标题将项目分成 `Custom` 和 `Default` 两类。可以把它理解成两种范围管理方式：沿用已有的任务与资源，或提出一个更自主的问题。无论哪一种，都要先核对课程当期的项目选项、提案格式、团队规则和资源限制；本页不代替这些要求。

自拟题目尤其要在开工前回答：

1. 最小可运行的实验是什么？
2. 现有时间和 GPU 资源能否完成它？
3. 如果新方法没有提升，结果是否仍能回答一个有用的问题？
4. 数据和代码能否合规使用并供团队复现？

## 3. 建立基线和受控比较

假设你要研究 LoRA rank 对分类效果的影响。一个可解释的设计可以是：

| 项目 | 固定或记录的设置 |
|---|---|
| 基线 | 冻结的基础模型、线性探针或课程允许的默认方法 |
| 变量 | LoRA rank，例如较小与较大的两个配置 |
| 尽量固定 | 数据划分、基础模型、训练步数、优化器、提示和评估脚本 |
| 效果指标 | 验证集指标与测试集指标，注明所用定义 |
| 成本指标 | 可训练参数量、峰值显存、训练时间 |
| 稳健性检查 | 固定数据版本；必要时用多个随机种子或报告波动 |

不要预设更大的 rank 一定更好。它增加模型适配能力，也会增加训练参数与计算成本；数据规模、优化设置和任务难度都会影响结果。项目的目标是清楚地检验关系，而不是先替结果下结论。

## 4. 结果之外还要做什么

- **数据检查**：查看样本来源、重复记录、空标签、类别分布和潜在污染。
- **指标检查**：写清楚指标公式、忽略的样本、汇总方式和主要局限。
- **误差分析**：列出模型在哪些输入上失败；区分事实错、格式错、检索错和标签噪声。
- **消融实验**：一次移除或改变一个关键组件，确认它对结论的作用。
- **复现记录**：记录代码版本、配置、种子、依赖、训练时长和硬件；保存评估脚本。
- **负结果说明**：报告失败配置、资源限制和不确定因素，不挑选单次最高分冒充稳定改进。

## 5. 小练习：设计一个可读的实验

**问题：**你想比较两个切片长度对检索问答的影响。先不要训练模型，请写下一个最小实验方案。

1. 指定一个语料、问题集、基础模型和检索器。
2. 只改变切片长度，其他配置保持一致。
3. 选一个回答质量指标和一个证据/成本指标。
4. 从错误案例判断改动是通过增加上下文、改善证据覆盖，还是只是增加了无关文本。

**自查：**如果两个配置使用了不同的语料或提示词，就不能把效果差异归因给切片长度；若只报告回答质量、不检查引用或检索结果，就无法知道性能变化发生在哪个环节。

## 6. 项目开工前检查

- [ ] 一句话说明问题和假设，避免把方法名称当成研究问题。
- [ ] 有可运行的基线、清楚的数据划分和预先确定的指标。
- [ ] 变量受控；实验的每次运行有配置与结果记录。
- [ ] 数据、模型、算力与使用条款都已确认。
- [ ] 团队成员能在自己的环境中复跑评估流程。
